    工作流程說明
    
  
    
    
    
    
    
  
    
  
    
    
    
      建議技能
      
    
        
    系統依目前輸入的字數與關鍵字，使用固定規則建議最多三種技能；建議不會自動執行，按下技能旁的按鈕才會啟用。
    
        
      
          
    1. 需求釐清：模型整理目前理解並提出 1–3 個問題，任務通常會停在「需要補充」。輸入少於 30 字，或包含「不知道、不確定、怎麼做、如何做、需求」等字詞時會建議。
      2. 
          
    2. 任務規劃：模型查閱必要資料後，列出執行步驟、相依關係與驗收條件，不會修改檔案。輸入包含「建立、新增、修改、改成、實作、開發、功能、頁面、程式、重構」等字詞時會建議。
      3. 
          
    3. 驗證檢查：模型根據取得的證據說明已驗證、尚未驗證及建議檢查項目，不會修改檔案。輸入包含「驗證、測試、確認、檢查、完成、正確、問題、錯誤、失敗」等字詞時會建議。
      4. 
          
    4. 若沒有符合任何規則，預設建議「需求釐清」；最多顯示三種。
      5. 
          
    5. 只有 real 模式會顯示技能建議；Mock 模式不會回傳建議。
      6. 
        
    
      
    
    
    
    
    
      自動整理記憶 (額外 token)
      
    
        
    一般專案要區分歷史篩選與記憶整理：預設可能使用 LLM 的是前者；#auto-memory-label 控制的是額外的後者。
    
        
    
          
    
            
    流程何時執行做什麼
    
            
              
    預設的歷史篩選一般任務送出時，處於 Real 模式、專案已授權 AI，且有候選任務從同一對話最近最多 6 筆合格文字任務中，讓 LLM 選出與本次要求相關的 0–6 筆，再交給執行任務的主請求。程式見 src/history-selection.js 與 server.js。
    
              
    自動整理記憶（額外 token）勾選後，通常在任務保存後；接近記憶預算門檻時也可能在送出前另發 LLM 請求，把合格任務、有效的已確認需求及既有結構化記憶整理成「目標、目前決定、限制、已完成、待辦與待確認」等項目。程式見 src/conversation-memory.js。
    
                
          
    
        
    
        
    沒勾選自動整理，也仍可能呼叫 LLM 篩選歷史；勾選後多了結構化記憶整理，歷史篩選仍照常進行。沒勾選時，超過 6 筆任務或保存 Edit 新版本會觸發不呼叫 LLM 的本機文字摘要（src/app-state.js）；一般任務的歷史主要由上述篩選流程決定，不能將本機摘要視為預設整份送給主請求。
    
        
    自動整理的材料不是固定只取最近 6 筆；圖片任務不納入這份一般對話記憶。若既有記憶來源失效，系統可能重新整理所有符合條件的文字任務。此選項僅 Real 模式顯示。
    
      
    
    
    
    
    
      對話記憶項目
      
    
        
    展開任務卡的「詳細資訊」後，可查看依來源任務 ID 對應的記憶項目。分類包括：
    
        
      
          
    • 目標：對話希望達成的結果。
      • 
          
    • 目前決定：已確認採用的選擇或方向。
      • 
          
    • 限制：執行時必須遵守的條件或避免事項。
      • 
          
    • 已完成：有紀錄可佐證已完成的工作。
      • 
          
    • 待辦與待確認：尚未完成、需要補充或仍待確認的事項。
      • 
        
    
        
    任務未產生可追溯的結構化記憶時，會顯示尚無對應項目的提示。此區顯示已保存的記憶來源，不代表「允許 AI 修改」已啟用。
    
      
    
    
    
    
    
      對話記憶
      
    
        未勾選自動整理記憶時：
        
      
          
    • 每次送出前固定保留有效的已確認需求與可用的明確限制；從同一對話最近 6 筆合格文字任務建立候選，再由篩選 LLM 選出 0–6 筆。
      • 
          
    • 明確限制目前取自來源仍有效的結構化記憶；若尚未建立或來源已失效，只有有效已確認需求會固定保留。重要限制可先確認為需求。
      • 
          
    • 選中任務的完整文字欄位與狀態會進入主請求；沒有選中的舊任務與舊附件圖片不會附上。
      • 
          
    • 篩選失敗時，主請求只帶本次需求與固定內容，並在任務追蹤中顯示原因。未勾選此開關不會略過歷史篩選。
      • 
        
    
        勾選自動整理記憶時：
        
      
          
    • 一般任務的歷史篩選與未勾選時相同：固定保留有效需求與可用限制，最多從最近 6 筆合格文字任務中選取 0–6 筆；不會因開關啟用就直接送出全部任務或結構化摘要。
      • 
          
    • 此開關另外控制任務保存後的背景記憶整理；若送出前需要更新記憶，預覽與實際固定內容可能不同。
      • 
          
    • 展開「對話記憶」後可預覽固定內容與標示「待篩選」的候選任務。送出前預覽不會呼叫篩選或記憶整理 LLM；送出後請在任務詳細資訊查看實際結果。
      • 
        
    
        自動整理記憶的另一個 LLM 請求：
        
      
          
    • 整理請求會使用先前結構化記憶、有效已確認需求，以及尚未納入記憶且符合條件的任務；必要時分批送出。這與一般任務收到的歷史上下文是兩個不同請求。
      • 
          
    • 編號清單是使用者在任務完成後按「確認為需求」保存的需求，不是 LLM 自動產生；勾選自動整理記憶時，有效項目會作為整理材料。
      • 
          
    • （有效）表示使用者確認為需求；（已被後續需求取代）表示確認以新需求取代舊需求，或編輯已確認任務並保存新版本。兩者都不是「確認套用」修改。
      • 
        
    
        一般任務共同送入資料與目前可見範圍：
        
      
          
    • Real 模式且有候選任務時，第一個 LLM 請求是歷史篩選：收到本次需求、固定內容與候選文字，不收到圖片。接著主請求才收到系統指令與可用工具、本次問題、選用技能、篩選後的 conversationContext，以及本輪選取的檔案和圖片資訊。只有關閉 MAGE_TEXT_ONLY_MODE 且實際選取圖片時，圖片內容才另以影像輸入送出；檔案全文要等模型使用讀取或搜尋工具才會進入後續請求。
      • 
          
    • 預覽位於 #memory-details 內的 #memory-summary，顯示送出前的固定內容與待篩選候選；不能把候選清單當成最終「已納入」。送出後在任務詳細資訊查看逐筆納入／排除理由、篩選材料，以及主請求實際收到的歷史上下文。
      • 
          
    • 輸入區的模型按鈕可選擇文字模型與思考深度，按對話保存；初始深度為「中」。每次操作固定送出時的設定，歷史篩選、主請求、記憶／圖片摘要、提示詞整合與完工整理沿用同一份快照，圖片生成維持獨立模型。停用或刪除模型後，舊對話需重新選擇才能送出新的文字請求。
      • 
          
    • 篩選 LLM 會逐筆回傳理由，但它仍可能漏掉有用的舊決定；因此有效已確認需求與可用的明確限制固定保留。Mock 模式會標示未送入 LLM。
      • 
          
    • 一般情況下 conversationContext 不含本次問題；延續／編輯任務可能會把完整需求附在上下文。預覽不含另行傳送的圖片實際內容及工具後續取得的檔案內容；若送出前需要更新自動記憶，實際固定內容可能改變。
      • 
        
    
      
    
    
    
    
    
      單張任務卡片 Delete
      
    
        以下是一般專案單張任務卡片的 Delete 操作，與側邊欄刪除整個對話不同。
        
      
          
    • 操作位置與確認
            
        
              
      • 每張一般任務卡片右上角有 Delete，與 Edit、View 並列。
        • 
              
      • 點擊後會開啟自製確認視窗，列出刪除影響；確認後才執行。
        • 
              
      • 圖片創作專案的任務不能透過這個按鈕刪除，畫面會提示原因。
        • 
            
      
          
      • 
          
    • 刪除範圍
            
        
              
      • 刪除一張任務卡片及其所有 Edit 版本，包含這些版本的任務紀錄。
        • 
              
      • 若卡片有多個版本，「需求版本」區和刪除確認視窗都會額外提醒。
        • 
              
      • 其他任務卡片保留。已寫入專案的檔案、共用備份與稽核紀錄也保留。
        • 
            
      
          
      • 
          
    • 已確認需求
            
        
              
      • 移除由被刪任務及其版本產生的已確認需求。
        • 
              
      • 如果被刪需求曾取代較早的需求，系統會依剩餘取代關係判斷：沒有其他需求繼續取代時，恢復較早需求為有效。
        • 
            
      
          
      • 
          
    • 摘要與歷史追蹤
            
        
              
      • 本機摘要依剩餘任務重新整理。
        • 
              
      • 結構化模型摘要及其更新紀錄，會移除涉及被刪任務或來源不明的項目，保留其他可追溯項目，並標示已刪改。
        • 
              
      • 刪除當下不會立即呼叫 LLM；後續記憶整理執行時才重建模型摘要。
        • 
              
      • 其他任務的歷史快照會移除被刪任務，以及無法安全拆分的固定內容、摘要與篩選理由；保留可辨識的其他候選任務，並標示快照已刪改。
        • 
            
      
          
      • 
          
    • 執行中任務與圖片
            
        
              
      • 目標任務若正在執行，系統會嘗試取消；已開始的檔案寫入則等待完成。
        • 
              
      • 同一對話的其他任務或記憶整理仍在執行，或等待超過 30 秒時，保留卡片並提示重試。
        • 
              
      • 一般生圖若尚未完整保存到專案歸檔，會阻止單筆刪除。歸檔完整時，專案內 PNG、JSON 和任務歸檔保留；中央 runtime 中可對應到該任務的 PNG／JSON 會嘗試清理，失敗時顯示警告。
        • 
            
      
          
      • 
        
    
        清除的限制：模型摘要的來源 ID 由 LLM 填寫，可能漏標，所以不能保證保留下來的摘要完全沒有被刪任務的內容。另外，後續任務自己的需求與回答原文會保留；若其中提到被刪內容，未來仍可能再次進入歷史上下文。

        服務流程分為啟動方式、服務啟動、初始監測與 API 驗證：

      • 
          
    • 服務啟動：系統掃描 Node 入口候選，確認入口與 Port 後啟動。專案外的 node_modules 路徑按專案保存；有服務正在啟動或執行時，該路徑會鎖定。
      • 
          
    • 啟動監測：啟動時檢查程序與 127.0.0.1 Port，之後每 30 秒檢查一次，最多五分鐘並記錄錯誤。
      • 
          
    • 監測與管理：五分鐘後停止定時監測與輸出擷取。服務面板只在開啟或手動操作時刷新；仍可查看初始監測結果及停止服務。也可用「關閉 3015」或「關閉服務」等自然語言停止目前專案內由服務管理器追蹤的服務，不需管理碼；若有多項服務且無法判定目標，會先詢問。
      • 
          
    • API 驗證：可設定方法、路徑、標頭、Body、預期狀態及回應條件；也可掃描最近已套用修改中的 Express 字串路由，選取後確認送出。
      • 
          
    • 執行界線：目前沒有任意 Bash／Shell 命令工具；服務以 Node 子程序啟動，依賴安裝限於指定的專案外目錄。

    BAT（可選）
→ PowerShell 啟動腳本
→ 設定環境變數與 API key

            圖片輸入模式最多 5 張，最新系列圖片也計入。圖片實際內容會轉成 Base64 data URL，作為 API 的圖片輸入送出；需要圖片專案允許外送，且模型端點支援圖片理解。MAGE_TEXT_ONLY_MODE = true 時仍可討論，但只送上述文字，不送圖片內容或圖片附件紀錄。
          
      3. 
          
    3. 創作草稿是什麼時候產生的？
            本輪圖片討論完成後，模型會回傳並保存「Agent 理解」、「參考圖片觀察」及候選完整提示詞，形成這一輪的創作草稿。文字模式下模型沒有收到圖片，「參考圖片觀察」不得當作已核對圖片內容。
            目前程式不會把上一輪的 imageProjectDraft.prompt 欄位直接固定帶入下一輪圖片討論。不過，如果上一輪的公開回答中包含提示詞，而該輪又被歷史篩選選中，模型仍可能透過公開回答間接看到那段文字。

      勾選「創作圖片」送出圖片創作
      
    
        勾選「創作圖片」後，系統會開啟確認視窗。按「開始創作」後，圖片模型會收到確認時的完整提示詞與圖片模型設定；只有圖片輸入模式且實際選用圖片材料時，才會另外收到圖片。
        
      
          
    • 完整提示詞
            
        
              
      • 預設不使用候選或上一版時，前端組合目前專案摘要、目前系列摘要與本次新增要求。
        • 
              
      • 選候選提示詞時，前端組合該版候選提示詞與本次新增要求；不再另外附加兩份摘要，也不呼叫整合 LLM。
        • 
              
      • 選「延續圖片 vN」並填入本次要求後，系統只追溯該版本的 previousJobId 祖先鏈，把各版要求與已保存提示詞、目前兩份摘要及本次要求交由文字 LLM 去重整合；不混入同系列其他分支。
        • 
              
      • 版本整合會顯示執行中、完成或失敗，以及採用內容、衝突與無法從文字核對的項目。請檢查產出的完整提示詞；失敗時不會悄悄改用舊版層層嵌入的文字。
        • 
              
      • 只有未使用整合紀錄、也未明確採用手動提示詞的舊式延續請求，後端才可能補上修改優先規則。使用新整合流程時，實際送出的文字與確認視窗一致。
        • 
            
      
          
      • 
          
    • 圖片材料
            
        
              
      • 上一版圖片：圖片輸入模式下選用時作為修改基礎，獨立於參考圖片清單；文字模式下只在畫面預覽。
        • 
              
      • 本次創作材料：確認視窗會列出選取的候選草稿所保存的參考圖，以及本輪貼入對話窗的草稿圖片。這些圖片會合併、依 ID 去重，預設不加入，需在確認視窗勾選。
        • 
              
      • 圖片輸入模式最多接受 5 張勾選的參考圖片。若另有一張上一版圖片，會再加入上一版，因此一次圖片編輯請求最多可能有 6 張圖片。文字模式下都不能勾選或傳送。
        • 
            
      
          
      • 
          
    • 送出方式
            
        
              
      • 沒有可傳送的上一版或參考圖片時，送出文字生成請求；MAGE_TEXT_ONLY_MODE = true 時即使選了延續版本也走文字生圖。
        • 
              
      • 圖片輸入模式且有圖片材料時，送出圖片編輯請求，使用 multipart/form-data 傳送圖片檔案內容，而不是 Base64 data URL。
        • 
              
      • 圖片服務回傳生成結果後，系統會將回應中的 Base64 圖片解碼並保存為 PNG。
        • 
            
      
          
      •

      MAGE_TEXT_ONLY_MODE（後端開關；目前 載入中）
      
    
        MAGE_TEXT_ONLY_MODE = true 時，仍可討論圖片和創作圖片；差異是輸入圖片不會送進 LLM 或生圖 API。
        
    
          
    項目原本圖片輸入可用時設為 true 後
    
          
            
    一般專案可選取圖片並隨任務送出草稿圖片不能勾選或送出；LLM 只收到文字
    
            
    圖片討論可將勾選的附件圖、最新系列圖送給 LLM仍送出本次要求、專案／系列摘要與符合條件的歷史文字；不送圖片內容，也不把圖片記為該任務附件
    
            
    圖片創作可把上一版圖片或參考圖交給生圖 API 編輯仍可創作；完整文字提示詞照常送出，但上一版圖、參考圖及草稿圖都不會送出
    
            
    延續上一版生圖模型可以讀取上一版圖片保留版本關聯；選延續版本時，由文字 LLM 整合祖先鏈與目前摘要及要求，再依文字重新生成，生圖模型看不到上一版圖片
    
            
    圖片選取介面依流程勾選圖片材料圖片仍可在畫面預覽，但圖片選項會取消勾選並停用；貼圖時會顯示自製提示窗

        文字中若提到圖片，描述文字仍可能送進模型，但圖片像素不會送出。設為 true 限制的是圖片輸入，不會停用圖片創作或阻止接收生圖結果。
      
    
    
    
    
    
      選擇來源並創作

    選單選項#image-create-full-prompt 的組成
    
            
              
    不使用候選提詞或上一版（預設）專案摘要＋系列摘要＋本次新增要求

    選延續版本時只走該版本的祖先鏈，不混入同系列的其他分支。若子版完整提示詞中精確包含父版全文，系統先移除這段重複文字，再分批交給 LLM；原始全文仍保存在整合紀錄。優先順序是本次要求、目前專案／系列摘要、祖先鏈由新到舊。
    
        
    選延續版本但本次要求空白時，系統會先提示填寫，不會啟動整合。確認視窗會顯示整合進度、採用與衝突說明，以及無法從文字核對的圖片要求；整合失敗時不會自動改用舊提示詞，可重新整理，或手動填寫並明確確認採用。
    
        
    你可以修改 #image-create-full-prompt；若修改後又更改來源或本次要求，手動文字會保留但標示已過期，必須重新整理或按「確認採用目前手動文字」才可送出。送出的文字長度須為 1–15000 字，且與任務卡保存的實際提示詞一致。
    
        
    整合來源、每批模型輸入與輸出、usage 及錯誤會保存在所屬系列的「提示詞整合紀錄」；若真的開始產圖，紀錄還會連結任務並保存最後送出的文字。取消產圖後，已有的整合紀錄仍可回查。整合過長時分批處理；結果超過 15000 字會再壓縮一次，仍超限則阻止送出。整合 LLM 無法看到圖片像素，文字模式下生圖 API 也不會收到圖片。

    歷史內容篩選與追蹤
    
  
    
    
    
    
  
    
  
    
    
    
      歷史內容篩選與 LLM 請求組裝
      
    
        
    可以把提示詞交給 LangChain 編排，但 LangChain 本身不會自動減少雜訊。要改善歷史內容與本次需求不相關的問題，仍要明確設計「依本次需求篩選歷史」的步驟。
    
        
    原本的組裝方式已有部分篩選：歷史只來自同一對話且符合外送條件的任務，但仍可能納入與本次需求無關的內容。因此現在先建立有限候選，再逐筆篩選與記錄結果。
    
        
    若要改善，建議拆成明確的兩階段：
    
        
      
          
    1. 依專案、授權與任務狀態取得可用歷史，再挑出有限的候選項目。
      2. 
          
    2. 用篩選請求根據本次需求，從候選項目選出相關任務 ID，並回傳選取理由。
      3. 
          
    3. 主請求只收到本次需求、必要規則、篩選後的歷史，以及必要的檔案或圖片資料。
      4. 
          
    4. 在 #memory-summary 顯示選入與排除項目及理由；篩選失敗時顯示提示，並採用明確的退回方式。
      5. 
        
    
        
    這會多一次 LLM 呼叫，增加延遲與 token 成本；篩選器也可能漏掉有用的舊決定。因此重要限制與有效確認需求應保留為固定上下文，再篩選一般任務歷史。LangChain 不會替系統決定篩選規則；可用 LangGraph 將流程拆成明確節點並按需要組裝上下文，也可以由現有程式自行實作。LangGraph 流程設計文件
    
        
    方向是加入可追蹤的歷史篩選流程，優化點是讓選入、排除與失敗退回都有紀錄，而不是單純把提示詞改交給 LangChain。
    
      
    
    
    
    
    
      可追蹤歷史篩選的實作與驗證計畫
      
    
        
    目前流程依下列範圍運作：
    
        
      
          
    • 一般專案：每次送出前，從最近 6 筆合格任務建立候選歷史；有效已確認需求與明確限制固定保留。篩選 LLM 可選 0–6 筆，並回傳逐筆納入或排除理由。選中的任務以完整文字欄位與狀態送入主請求。
      • 
          
    • 圖片討論：第一階段只看本次需求、專案／系列摘要及同系列最近 6 筆討論文字，不分析圖片；第二階段才收到篩選後的歷史、摘要、本次需求與本輪選取圖片。
      • 
          
    • 預覽與追蹤：送出前顯示固定內容及最多 6 筆候選歷史，明確標示「待篩選」；送出後自動接續主請求，並可查納入／排除理由、篩選 LLM 收到的候選文字，以及主請求實際收到的歷史上下文。
      •

      一張圖片的創作資料
      
    
        
    以目前專案的區塊來看，一張圖片的創作資料可以拆成這幾層；其中「系列摘要」描述這一系列要延續的方向，並不等於某一張圖的完整風格設定。
    
        
    
          
    
            
    層次對應目前專案負責的內容
    
            
              
    跨系列共通設定專案摘要品牌、常用風格、比例、色彩與禁止事項
    
              
    這一組圖片的方向系列摘要主題、構圖、已決定的版本方向與待調整事項
    
              
    本輪想改什麼本次要求例如「只改成藍色系，其他內容保留」
    
              
    討論形成的提案候選提示詞版本圖片討論產出的創作草稿；可選用，但不會自動變成正式摘要
    
              
    真正用來產圖的文字完整提示詞預設或選候選時由前端組合；選延續版本時由文字 LLM 整合祖先鏈與目前摘要、要求；可在確認視窗手動修改，最後送往生圖 API
    
              
    視覺依據上一版圖片、參考圖、草稿附件依選取狀態使用；MAGE_TEXT_ONLY_MODE = true 時只供畫面查看，不送圖片內容
    
              
    產出與追溯圖片 v1、v2…及任務紀錄保存 PNG、實際完整提示詞、摘要版本快照及上一版關聯
    
                
          
    
        
    
        
    如果目標是「保留圖二的內容與排版，只換配色」，最直接的對應是：選「延續圖片 v2」，在本次要求寫明只改配色，再檢查版本鏈整合後的完整提示詞與無法核對項目。只選系列摘要或早期候選提示詞，未必包含圖二每個區塊的細節。在文字模式下，生圖模型仍只能依整合後的文字重建，無法看到 v2 的像素，因此不能保證版面完全一致。
