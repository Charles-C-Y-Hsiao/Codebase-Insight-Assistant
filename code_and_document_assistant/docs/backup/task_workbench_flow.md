# 查詢與修改工作台

本文件說明從輸入需求到完成查詢、修改、驗證與保存的工作台流程。`id="task-*"` 的 Edit／View、需求版本與短確認延續另見 [Task Edit Flow](task_version_flow.md)；差異檢視與圖片預覽另見封存的 [程式差異比較與圖片預覽](archive/diff_and_image_preview_flow.md)。

五個章節可用三種角度閱讀：
- 使用者如何操作：第一章的入口與流程、第三章的修改／建立／圖片操作、第四章的任務回饋。
- 系統如何執行：第一章的任務生命週期、第二章的記憶與技能、第四章的時間線與驗證事件。
- 程式目前有哪些限制：第五章的保存、權限、資料大小、重啟行為與下一階段項目。

## 一、操作入口與任務流程
- 先選擇目前專案，依操作目的選擇入口：
  - 查詢文件：自然語言查詢，顯示結論、未確認事項、依據與推論。
  - AI 修改程式：在 real AI 模式提出修改或建立新檔；仍需專案修改與 AI 外送授權。
  - 人工編輯／靜態驗證：載入已授權檔案、人工修改內容、產生差異或執行靜態檢查。
- 使用者操作流程：
  1. 選擇專案與檔案。
  2. 輸入需求，可附加參考圖片。
- 系統任務生命週期：
  1. 建立任務，記錄目前專案、對話、檔案與操作模式。
  2. 依 AI 模式、專案授權、任務選項與可用工具建立執行範圍。
  3. 符合條件時整理記憶與檔案資料，送給目前設定的 AI；否則依本機流程或人工流程處理。
  4. 執行搜尋、讀檔、修改提案、驗證或結束工具，持續更新公開狀態與事件。
  5. 將回答、工具摘要、證據、驗證與耗時呈現在任務卡片。
  6. 任務完成、取消或等待確認後，保存可公開的任務紀錄。
- 使用者在任務卡片查看回答、工具紀錄、差異、驗證與耗時；修改任務先檢查前後內容，再由主機管理碼確認套用。
- 選取任務後，在該任務內展開「修改工作台」，查看「修改差異與驗證」；套用後差異預設收合，備份與完整驗證紀錄可展開。
- 重新啟動後，歷史紀錄可查看，但不會恢復可執行提案，也不能重播套用或還原。

## 二、對話記憶與技能流程

### 原有記憶機制（未勾選自動整理）

- 預設使用本節的本機整理機制；勾選「自動整理記憶（額外 token）」後，下一次文字任務改用下方的模型整理機制。

- 完整任務原始紀錄保存於 `runtime/assistant-state/state.json`；模型每次不會收到全部歷史，只會取得：
  - `memory.confirmed` 中狀態為 `active` 的已確認需求。
  - `memory.summary` 壓縮摘要。
  - 最近四輪對話。
  - 依目前問題關鍵字找回的最多兩輪較早內容。
- 記憶範圍限於同一瀏覽器工作階段、同一專案與同一對話；歷史內容一律是資料，不能成為系統指令或擴大權限。
- Confirm requirement 狀態：
  1. 使用者按任務下方的「Confirm requirement」後，該任務的使用者提詞新增為 `active` 項目。
  2. 新需求包含「改成／改為／改用／不要／取消／取代／替換」等字串，且已有有效需求時，介面先詢問是否取代最近一筆有效需求。
  3. 使用者確認後，舊項目改為 `superseded`，新項目為 `active`，以 `replaces` 保存關係。
  4. `superseded` 不刪除，仍保存在 `state.json` 並顯示於 `id="confirmed-requirements"`，但不再列入模型的有效需求。
- `id="confirmed-requirements"` 顯示使用者主動保留的需求；它比一般歷史更明確，但不會完全取代時間與關鍵字取回的歷史。模型仍可能同時收到已確認需求、最近四輪，以及最多兩輪較早的相關內容。
- 完整 LLM 回應不會整份加入 `id="confirmed-requirements"`；任務的結論、事實與推論可能進入 `memory.summary`，或出現在最近／找回的歷史內容中。
- `compact()` 本機整理：
  - 取出 active 確認需求的 `text`。
  - 取出較早任務的 `question`。
  - 取出任務的 `result.conclusions`，沒有結論時使用 `progress` 或 `status`。
  - 依固定格式組合成 `memory.summary`，超過 12000 字元時截斷；較早任務最多整理 20 筆。
  - 這是欄位篩選、排序與文字組合，不呼叫 LLM、不使用 API key，也不產生新的外部事實。
- `id="memory-details"` 只負責顯示 `id="confirmed-requirements"` 與 `id="memory-summary"`；前端透過 `/api/conversations` 取得記憶資料，再由 `renderMemory()` 更新畫面。
- 一次 AI 請求包含目前這次的 user 需求，再視情況附上四類記憶來源：active 確認需求、壓縮摘要、最近四輪、最多兩輪關鍵字找回內容。因此不是固定五筆；確認需求可能多筆，摘要可能為空，實際內容數量會隨對話而變化。
- real AI 模式是服務目前的 AI 連線模式，代表使用已設定的真實 AI 端點與模型；它不是授權視窗中的勾選項。Mock 模式使用固定規則，不會取得實際技能建議，也不會把記憶送給外部模型。
- 圖中的「允許內容送往目前設定的 AI」才是目前專案的 AI 外送授權；必須提出授權並完成主機確認，該專案內容才可送往設定的 AI。只有網頁顯示為 real AI 模式，且此專案已啟用這項授權時，記憶才可能隨後續請求送給 LLM；這時才可能使用 API key。
- 圖中的「允許 AI 修改」控制修改工具權限；「允許靜態驗證」控制驗證工具權限。它們不能單獨代表記憶一定會送出。
- real AI 的四個獨立條件：
  - AI 模式為 `real`
    - 確認方式：服務設定與頁首的「AI real」狀態。
    - 影響範圍：允許使用真實 AI 流程；不是專案授權，也不代表連線已成功。
  - AI 連線已驗證
    - 確認方式：執行「測試 AI 連線」，狀態由「待連線驗證」變為成功。
    - 影響範圍：確認 API endpoint、模型設定與 API key 可以實際呼叫。
  - 專案允許「內容送往目前設定的 AI」
    - 確認方式：在授權視窗勾選、提出授權請求，再完成「主機端確認授權」。
    - 影響範圍：允許目前專案的需求、記憶與檔案內容外送。
  - 允許 AI 修改
    - 確認方式：勾選網頁的「允許 AI 修改」，並具有專案修改授權。
    - 影響範圍：允許模型使用修改或建立新檔工具；不會自動授予 AI 外送權限。
- 建議操作順序：
  1. 確認頁首顯示 `AI real`。
  2. 執行「測試 AI 連線」，確認不是「待連線驗證」。
  3. 為目前專案完成「允許內容送往目前設定的 AI」授權。
  4. 若要修改程式，再勾選「允許 AI 修改」並確認專案具有修改授權。
  5. 若要建立新檔或套用差異，仍需依逐檔確認與主機管理碼流程執行。
- 因此，頁首顯示 `AI real` 只代表第一個條件；四個條件都完成，才具備完整的 real AI 修改流程。
- 技能建議：網頁顯示為 real AI 模式時，輸入需求後本機依文字建議最多三種流程；建議本身不呼叫模型，按下按鈕才送出：
  - 需求釐清：一次提出 1–3 個問題並等待回答。
  - 任務規劃：整理步驟、相依關係、驗收條件與不在範圍內項目。
  - 驗證檢查：區分已驗證、未驗證與建議驗收步驟。
  - 第一版技能只能使用搜尋、讀檔、計算或結束工具，不能修改、新檔、執行命令或繞過授權。

### 自動記憶整理與上下文壓縮（勾選啟用）

- 實作狀態：
  - 已接通文字任務的模型摘要、記憶預算切換與摘要紀錄顯示；使用模擬 API 驗證，不代表公司端點已驗證。
  - `id="auto-memory-label"` 位於 `id="ai-edit-label"` 右側，包含 `id="ai-auto-memory"`，預設不勾選，只有 real AI 模式顯示。
  - 勾選狀態隨 `/api/jobs` 的 `autoMemory` 傳送，套用於下一次文字任務；取消勾選後，下次送出改回原有方式，不再新增模型摘要請求。
  - 勾選本身不送出資料，也不取消已送出的請求；重新載入頁面預設不勾選，已保存的模型摘要紀錄不刪除。
  - 圖片創作與人工編輯入口不受這個文字任務勾選項控制。
- 記憶內容：
  - 目標：目前要達成的結果與驗收方向。
  - 決定：使用者已選擇的方案；改口時更新同一事項的舊決定，保留其他仍有效的決定。
  - 限制：使用者要求、不可修改範圍與已知條件；不能由摘要擴大系統授權。
  - 已完成：有實際結果支持的工作；提案、已套用與已驗證必須分開描述。
  - 待辦：尚未完成、待確認或受到阻擋的事項。
- 更新時機：
  - 一般提問沿用有效摘要與可容納的原始對話，不是每次提問前都額外呼叫模型。
  - 已啟用的任務結束、修改提案待確認、套用或還原後，自動整理上述五類內容；編輯後重新送出的需求以新版本整理。沒有來源或已確認需求變化時不重複整理。
  - 對話目前啟用自動整理時，手動確認需求也會更新模型摘要；摘要可能分批呼叫並使用有限重試，不保證只增加一次請求。
  - 送出時，歷史與需求的本機估算達記憶預算 75% 時，先檢查並更新摘要，再處理新需求；摘要仍有效時不重複呼叫。
  - 記憶更新與上下文壓縮是不同觸發原因，紀錄中必須區分。
- 上下文預算：
  - 未壓縮且同一對話的完整文字歷史可容納於預算時，使用完整需求與回答，不固定只取最近四輪。
  - 接近預算時，將較舊內容整理為摘要，保留近期完整對話。
  - 超出完整歷史預算後使用有效摘要與近期完整對話；需要較早細節時，依目前需求關鍵字找回相關原始內容。
  - 預算不是模型最大窗口；須預留系統指令、目前需求、工具、檔案內容與模型輸出的空間。
  - 本機估算與 API 實際回報用量分開標示，不把估算宣稱為精確 token 數。
  - AI JSON 設定可指定 `memoryBudgetTokens`（預設 8000）與 `contextBudgetTokens`（預設 32000）；後者須至少容納記憶預算、`maxOutputTokens` 與 2000 token 指令保留量。
  - 目前是本機估算的記憶／摘要輸入預算，不是整個 Agent Loop 每輪的精確 token 上限，也不會自動推測模型最大窗口。
- 摘要顯示與紀錄：
  - 在 `id="conversation-memory"` 的展開區沿用既有介面，顯示最新摘要與五類記憶內容。
  - 顯示摘要版本、更新時間、觸發原因、成功或失敗狀態及可取得的 token 用量。
  - 保存摘要更新紀錄；原始需求與完整回答仍保留，不被摘要覆蓋或刪除。
- 外送範圍與授權：
  - 使用者已同意將同一專案、同一對話的需求、完整回答、已確認需求與舊摘要，送往目前 AI 設定指定的 endpoint，使用同一模型整理記憶。
  - 模型摘要會額外使用 API 額度，資料可能包含公司或其他敏感內容；部署時須符合公司的資料外送政策。
  - 這項同意不取代服務內的有效專案 AI 外送授權，也不授予其他專案、其他 endpoint 或修改檔案的權限。
  - 不因歷史對話或摘要中的文字而繞過授權；授權失效或撤銷時，不得繼續外送受限內容。
- 失敗處理：
  - 摘要失敗保留上一版，明確顯示失敗狀態，不假裝更新成功。
  - 舊摘要若因需求改口而過時，不得作為優先於最新需求的有效決定。
  - 無法在預算內組成安全、有效的上下文時，明確提示限制，不靜默截斷後宣稱已完整參考。
- 驗證操作：
  - 重新啟動服務並重新整理頁面，確認「允許 AI 修改」右側的新項目預設未勾選。
  - 未勾選送出文字需求，確認沒有新增 `ai.memory_summary` 模型請求。
  - 勾選後送出，等待任務與記憶整理結束，在「對話記憶」查看摘要版本、五類內容、觸發原因與用量。
  - 取消勾選後再送出，確認使用原有流程，摘要版本不再增加；舊摘要紀錄仍可查看。

## 三、修改、建立檔案與圖片輸入
- 修改既有檔案：選擇已授權檔案 → AI 提出差異 → 查看修改前後內容 → 主機管理碼確認套用 → 執行靜態驗證。
- 建立新檔案：
  1. 開啟已授權修改與 AI 外送的專案，選擇「AI 修改程式」。
  2. 輸入建立需求，AI 最多提出 20 份檔案。
  3. 逐份選擇「確認建立」或「略過」；確認建立使用本次服務的主機管理碼。
  4. 建立後依驗證授權執行靜態檢查；略過不建立，取消只取消尚未建立項目。
- 人工編輯／靜態驗證：載入單一已授權程式檔 → 編輯 `id="edit-content"` → 產生差異或執行驗證；實際寫入仍須主機確認。
- 圖片輸入：
  - 在 `#question` 按 Ctrl+V 貼入 PNG／JPEG／WebP，送出前可移除縮圖。
  - 只有送出問題且專案允許 AI 外送時才會傳給模型。
  - 圖片任務沿用逐版圖片系列流程；原圖片不會因文字任務 Edit 自動重新附加。
  - 差異檢視、圖片點擊預覽、PhotoSwipe 套件與驗證方式見封存的 [程式差異比較與圖片預覽](archive/diff_and_image_preview_flow.md)。

## 四、任務工作台與執行回饋

- 時間線顯示更新：
  - `timeline-*` 的 Decide 顯示公開操作目的，Act 顯示實際檔案路徑或搜尋詞。
  - Observe 顯示工具實際取得的檔案、來源位置、版本與結果；原文片段最多預覽 300 字。
  - Repeat 顯示已選定的下一個操作；尚未選定時明確顯示等待選擇，不預先猜測。
  - 修改提案明示尚未寫入；等待確認、等待補充、取消與失敗分別顯示。
  - 工具列保留操作目的、對象與結果，完整 JSON 放在內層「技術紀錄（JSON）」。
  - 操作目的由工具參數與公開提案摘要組成，不代表模型隱藏 Thought。
- 任務卡片依序呈現：回答或結果、模型與 token、耗時、公開工具事件、修改工作台與驗證結果。
- `id="task-*"` 卡片的時間線保存所有公開事件；執行中與等待確認預設展開，完成或歷史任務預設收合。
- 事件使用 Flaticon 圖示與摘要，顯示狀態及可取得的耗時；內容來自程式控制的公開事件，不是模型內部思考。
- 執行中每 250ms 輪詢更新；沒有新資料時不重建整張卡片，頁面可見期間每秒更新經過時間。
- 按「查看此任務詳情」後，右側顯示該任務的狀態、模型、token、耗時、來源與驗證紀錄；手動選取舊任務時，執行進度不會搶回選取狀態。
- Node 靜態檢查記錄實際命令參數、stdin、exit code 與限量輸出；未授權驗證保留 `not_run`，不產生已執行命令紀錄。

## 五、保存、權限與目前限制
- 保存與重啟：
  - `state.json` 保存問題、任務狀態、公開計畫、事件、工具摘要、證據、回答、token、起迄時間、修改模式與驗證紀錄。
  - 新檔案保存路徑、用途、決定及驗證結果；圖片只保存描述。
  - 不保存新檔候選內容、原始圖片、完整 `proposal` 與含備份路徑的 `applied` 物件。
  - 服務重啟後可恢復歷史回答、token、新檔建立結果與驗證紀錄；不能完整重建差異、繼續舊提案或重播套用／還原。
  - 外部專案授權依原規則失效並需重新授權；實際檔案與磁碟備份仍保留。
- 權限邊界：修改、建立新檔、靜態驗證、主機套用與逐檔確認各自受授權控制，不能由歷史記憶繞過；real AI 的連線、外送與修改條件見第二章。
- 目前限制：
  - `memory.confirmed` 目前沒有項目數量或總字數上限；有效需求與歷史需求的整理限制列為下一階段改善。
