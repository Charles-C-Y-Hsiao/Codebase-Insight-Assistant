# Agent Loop：目前工具能力與 Act 分類

本文件記錄目前專案助手的工具能力，並區分專案助手與 Codex 開發環境所使用的指令。

這份文件共有 5 個第一階重點：

- 三層視角與增量迭代原則：介面層、互動層與 Harness 層
- Codex 開發環境與專案助手的差異
- Agent Loop 對照與各功能的對應
- 下一階段可補強的能力
- PLAN／EDIT／VERIFY 的分工

## 三層視角與增量迭代原則：介面層／互動層／Harness 層

這是閱讀整個專案最適合的起點。每次調整前，先判斷它主要屬於哪一層，再確認是否會牽動其他層。

### 介面層：使用者看見什麼

- 位置、間距、圖示、tooltip、展開與收合。
- 任務卡片、時間線、差異與驗證紀錄如何分組顯示。
- 目的不是逐像素複製 Codex，而是讓使用者容易理解目前狀態與下一步。

### 互動層：使用者可以做什麼

- 按鈕切換的狀態、顯示時機與可操作條件。
- 使用者選取專案、提出需求、確認修改或取消操作時，畫面如何回應。
- 例如隱藏 `#mode-query` 不只是介面調整，也會改變取消「允許 AI 修改」後的回復方式；因此必須明確回到 query 模式。

### Harness 層：系統允許 Agent 做什麼

- 模型可使用哪些工具、可讀寫哪些檔案，以及需要哪些授權。
- 何時等待使用者確認、如何建立備份、如何驗證，以及如何留下可核對的紀錄。
- 這一層決定專案是否能從「有 Agent 介面」變成實際可用的 Harness。

### 每次調整的最小規劃

先用一句話說明目的，例如：

- 讓使用者知道目前正在修改哪個專案。
- 減少固定區塊高度，讓對話區有更多空間。
- 讓使用者在套用前能確認這是實際寫入。

再確認三件事：

1. 這是純介面、互動，還是 Harness 規則？
2. 這個改動是否會影響未來的真實 LLM 流程？
3. 如何確認使用者真的能完成這項操作？

這能保留改動的目的與脈絡，避免只從 CSS 選擇器或 DOM ID 開始修改。

### 參考 Codex 時的待辦格式

把觀察轉成小型待辦，吸收設計原則而非逐像素重做：

```text
觀察：Codex 顯示工具執行紀錄
目的：讓使用者知道 Agent 做了什麼
你的版本：#tools、#events、#plan
下一步：讓真實 LLM 工具結果也進入同一套紀錄
```

### 核心流程優先順序

維持「看到問題就修」的節奏，但每完成數個 UI 調整，就補強一條可實際操作的完整流程：

```text
選定專案與授權
→ 搜尋／讀取檔案
→ LLM 提出差異
→ 使用者確認
→ 主機寫入與備份
→ 靜態驗證
→ 顯示可核對的紀錄
```

這條鏈比多 Agent、Docker 或子任務排程更優先，因為它直接決定 Harness 是否能實際使用。後續介面調整若可能影響權限、任務狀態、工具流程或 LLM 整合，應先說明影響與較合適的做法，再進行實作。

## Codex 開發環境與專案助手的差異

在 Codex 執行開發任務時，畫面可能會看到 `Get-Content`、`rg` 或 PowerShell。這些是 Codex 開發環境用來檢查專案的指令，不代表目前專案助手本身可以直接執行任意 Shell 或 PowerShell 指令。

### 使用 API key 可以做到什麼

這裡的 API key 是提供給專案後端使用的 OpenAI API 金鑰，不等同於 Codex 應用程式本身的工作區權限、終端機權限或原生介面。

使用 API key 可以讓專案建立類似 Codex 的 Agent Loop：

- Thought（隱藏）
  - 模型可以進行內部推理。
  - 原始模型內部思考不應直接顯示給使用者。
  - 如果需要，可另外要求模型產生簡短的計畫或行動摘要。
- Decide
  - 模型根據需求、上下文與工具定義，決定下一步。
  - 例如決定使用 `read_file`、`search_documents`、`propose_edit` 或 `finish`。
- Act
  - 模型提出工具呼叫。
  - 專案後端實際執行受控工具，例如讀取檔案、搜尋文件、提出修改或執行固定驗證。
- Observe
  - 專案後端將工具結果回傳給模型。
  - 內容可以包含搜尋結果、檔案內容、修改差異、錯誤與驗證結果。
- Repeat
  - 如果結果不足以完成任務，模型可以要求下一個工具。
  - 後端依設定限制最大輪數、工具次數、輸出長度與執行時間。
- Stop
  - 模型不再要求工具，或後端判定任務需要停止。
  - 也可能因為等待使用者確認、發生錯誤或達到執行上限而停止。
- Final Answer
  - 模型整理結論、依據、推論、未確認事項與驗證結果。
  - 介面再將公開摘要呈現給使用者。

### API key 不會自動提供的能力

即使擁有 API key，以下能力也不會自動出現，必須由專案後端自行實作並加上權限控管：

- 任意執行 PowerShell
- 任意讀取本機檔案
- 任意修改本機檔案
- Codex 的原生執行紀錄介面
- Codex 的隱藏 Thought
- 自動安全控管與使用者授權

模型只能提出工具呼叫；真正能否讀取、修改或執行，取決於後端是否提供該工具，以及工具本身的路徑、權限、時間與輸出限制。

### 對照 Codex 畫面

圖一中的 `Designing JS-powered fixed-position tooltip` 比較接近公開的工作摘要或 `Decide`：

- 表示目前決定要設計固定位置的 JavaScript tooltip。
- 不是原始的 Thought。
- 原始 Thought 應保持隱藏。

圖二中的內容可以拆成：

- `Decide`
  - 決定先搜尋 `renderFiles`、`files` 與 tooltip 相關程式。
- `Act`
  - 執行 `rg`、`Get-Content` 或其他受控工具。
- `Observe`
  - 取得搜尋結果、檔案內容與目前實作狀態。
- `Repeat`
  - 根據結果繼續搜尋、修改或驗證。

因此，專案時間線應公開顯示工具行為與結果摘要，例如：

```text
Decide：規劃 tooltip 顯示方式
↓
Act：搜尋 renderFiles 與相關 CSS
↓
Observe：找到檔案清單目前顯示完整路徑
↓
Act：修改 public/app.js 與 public/styles.css
↓
Observe：靜態檢查通過
↓
Stop：等待使用者確認或完成任務
↓
Final Answer：整理修改內容與驗證結果
```

API 的工具呼叫本身可以形成多輪流程，但 Codex 的 UI、工作區權限、終端機整合、原生執行紀錄與安全沙箱，不會因為提供 API key 就自動複製到專案中。

## Agent Loop 對照

目前專案與圖中的 ReAct 流程可對照為：

- Thought
  - 對應 AI 的內部推理。
  - 目前不直接公開模型內部思考，只公開後續行動摘要。
  ↓
- Decide
  - AI 判斷下一步要使用哪個工具。
  - 例如決定使用 `read_file`、`search_documents` 或 `finish`。
  ↓
- Act
  - 執行受控工具，例如 `read_file`、`search_documents`、`calculate`、`propose_edit`。
  ↓
- Observe
  - 讀取工具結果、檔案內容、證據與驗證結果。
  ↓
- Repeat 或 Stop
  - Repeat：結果不足以完成任務，將 Observation 放入下一輪上下文。
    - → 回到 Decide
  - Stop：停止目前循環。
    - 可能是完成回答。
    - 可能是等待使用者確認修改或建立檔案。
    - 可能是發生錯誤、部分完成或達到執行上限。
  ↓（只有需要整理回答時）
- Final Answer
  - 通常由 `finish` 工具整理結論、依據、推論與未確認事項。
  - 再由介面顯示給使用者。

簡化流程：

```text
Thought（隱藏）
  ↓
Decide → Act → Observe
           ↑       │
           └─ Repeat
                   │
                   ↓ Stop
             finish → Final Answer
```

注意：`Stop` 不一定等於 `Final Answer`。如果是修改或建立檔案提案，`Stop` 可能代表暫停並等待使用者確認。

### 目前能力的對應關係

- `read_file`：受限制版的 `Get-Content`，只能讀取授權範圍內的檔案。
- `search_documents`：受限制版的 `rg`，只能搜尋允許的文件範圍。
- `calculate`：執行受限制的數值計算。
- `propose_edit`：提出既有檔案修改方案，等待使用者確認後才套用。
- `propose_new_files`：提出新檔案建立方案，依規則等待使用者逐檔確認。
- 靜態驗證：後端可使用 Node/Python 執行固定的驗證流程，但這不是 AI 可任意呼叫的 Shell 工具。

### 時間線如何呈現 Agent 的受控操作

讀取、搜尋與驗證都可以歸類到 Agent Loop 的 `Act` 或 `Observe`，但時間線應呈現受控操作的語意，而不是直接顯示開發環境指令：

```text
Act：讀取檔案
Act：搜尋檔案
Observe：取得搜尋結果
Observe：驗證完成
```

不應直接呈現為：

```text
Act：執行 PowerShell Get-Content ...
```

## 下一階段：從目前邊界繼續補強

目前沒有開放以下能力給專案助手：

- 任意 PowerShell 指令
- 任意 Shell 指令
- 任意程式執行
- 未受限制的網址或系統資源存取

### 下一步：增加受控 Shell 工具時的條件

若未來要讓專案助手更接近 Codex 的執行方式，應增加受控而非任意的 Shell 工具，至少需要限制：

- 可執行的指令白名單
- 固定或受限的工作目錄
- 檔案與路徑邊界
- 輸出內容長度
- 執行時間
- 使用者授權與確認流程
- 完整的時間線與稽核紀錄

避免直接開放任意 PowerShell，降低命令注入、越權讀寫與未授權程式執行的風險。

## 操作模式：PLAN／EDIT／VERIFY

目前三者不是相同類型的功能：

功能分類如下：

- PLAN／任務規劃
  - 目前性質：建議技能。
  - 是否修改檔案：否。
  - 可觀察結果：產生步驟、相依關係與驗收條件。
- EDIT／修改
  - 目前性質：實際操作流程。
  - 是否修改檔案：可以，但需要使用者確認。
  - 可觀察結果：差異預覽、套用、備份與靜態驗證。
- VERIFY／驗證檢查
  - 目前性質：建議技能。
  - 是否修改檔案：否。
  - 可觀察結果：整理已有證據、未驗證項目與建議測試。

### PLAN

`plan-task` 是唯讀的任務規劃技能，會使用 `search_documents`、`read_file`、`calculate` 與 `finish`，把需求拆成小步驟、相依關係、驗收條件，以及不在範圍內的項目。它不會修改或建立檔案。

### EDIT

EDIT 是目前最容易觀察到結果的流程，因為它會提出修改差異，等待使用者確認後才套用，並保留備份與驗證結果。

### VERIFY

`verify-result` 是唯讀的驗證檢查技能，會使用搜尋與讀檔結果區分：

- 已有證據
- 只完成靜態檢查的項目
- 尚未執行的功能驗證
- 建議人工測試步驟

它不會自動修改檔案，也不會把寫入成功或靜態檢查誤認為完整功能測試。

### 目前的可驗證範圍

- `plan-task` 與 `verify-result` 已註冊為唯讀技能。
- 兩者都不能使用 `propose_edit` 或 `propose_new_files`。
- 單元測試會驗證建議技能可以出現，且不會自動修改檔案。
- EDIT 流程則有瀏覽器測試驗證修改、確認、套用、靜態驗證與還原。

因此 PLAN／VERIFY 有功能，但屬於「只讀分析技能」；EDIT 才是會產生明顯外部結果的執行流程。

若要讓 PLAN／VERIFY 更容易觀察，時間線可以顯示類似以下的公開摘要：

```text
PLAN
已讀取 3 個檔案
已拆出 4 個執行步驟
已列出 2 個驗收條件
未修改任何檔案
```

```text
VERIFY
已檢查 3 個檔案
HTML 靜態檢查：通過
瀏覽器功能測試：未執行
仍有 2 項待人工確認
```
